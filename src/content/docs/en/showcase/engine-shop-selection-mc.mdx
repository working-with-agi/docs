import { Aside, Card, CardGrid } from "@astrojs/starlight/components";

Airline engine maintenance planning means deciding, every month, **which engine goes to which shop, when, and with what workscope**. The inputs are scattered: shop quotes, shop manuals, contracts, reliability data, budgets. This showcase shows how to **use the WorkWithAGI SDK to have AI agents run this planning work**, organised by business use case.

The computation itself (stochastic programming, Monte Carlo) is done by the Python scripts in the SDK repository examples. The SDK handles everything around it: **collect the data → agents solve → show results to people for a decision → run again next month**.

<Aside type="caution" title="About the data">
  Every number on this page comes from running the SDK repository example (`examples/engine-shop-selection-mc/`) on **synthetic data** (a 737-800-like fleet: 62 aircraft, 124 installed positions, 136 owned engines, 44 shop visits due in two years; units k$). They are not quotes or actuals from any OEM, shop or airline. Results depend heavily on assumptions — calibrate with real data before use.
</Aside>

## What planners and executives get

<CardGrid>
  <Card title="Decisions due this month" icon="warning">
    Each monthly run lists **the engines that must be decided this month**, why (shop slot booking or LLP kit lead time), and what hurrying or waiting would cost.
  </Card>
  <Card title="A report with a conclusion" icon="document">
    The requirements (cancellation-risk target, spare buffer, fiscal budget, minimum volumes, …) cannot all be met. The report (`report.html`) concludes along their priority: **recommended plan, decisions due now, approvals needed**.
  </Card>
  <Card title="Decision room" icon="approve-check">
    A page (`room.html`) where each decision is **approved / held / returned** and shared, with an AI side panel you can ask about the analysis ("what if E-104 moves to next month?").
  </Card>
  <Card title="Parallel what-ifs" icon="random">
    "What if MRO shops are congested", "what if LLP kits are short", "what if mid-life engines are cheap" — solved **in parallel in separate agent sessions** and compared on the same evaluation scenarios.

## Architecture: which SDK pieces are used

```
 (1) Knowledge                    (2) Agents (sandbox)                      (3) Outputs
 ─────────────────────────       ─────────────────────────────────         ──────────────────────
 KnowledgeClient                  AgiApiClient.createSession               report.html
   upload()  quote PDFs, contracts ─► planner : shape data, run scripts ─►   (conclusion, approvals)
   upload()  shop manuals              addPane({ role: "reviewer" })         room.html
   upload()  reliability CSV           reviewer: check assumptions,          (shared approvals + AI Q&A)
   connect() SharePoint / Drive                  contract reading            compare.html
             (scheduled sync)          parallel: one session per what-if     (method chooser)
   context() excerpts into prompts     Promise.all([createSession, ...])     WorkAGI.terminal embeds
                                                                             the agents' work
          ▲                                                                          │
          │                                                                          ▼
 (4) Triggers  ─────────────────────────────────────────────────────────────────────────────
   monthly run (1st of the month)  /  meeting-note events (Secretary.io: "E-104 teardown findings")
   /  replaced quotes (knowledge sync)                                    → run (2) again
```

| Piece | Status | Use |
|---|---|---|
| `KnowledgeClient.upload / search / context` | **In the SDK** | Ingest quotes, manuals and reliability data; pass contract terms and TAT excerpts into prompts |
| `KnowledgeClient.connect / sync` (with `schedule`) | **In the SDK** | Periodically sync quote folders on SharePoint, Google Drive, etc. |
| `AgiApiClient.createSession / addPane / destroySession` | **In the SDK** | Start agents in a sandbox, with planner and reviewer role panes |
| `WorkAGI.api / terminal / connect` | **In the SDK** | Create the API client, embed the working terminal in a page, headless connection |
| Report, chooser and decision-room HTML | **In the example** | Single-file HTML generated inside the sandbox by `decide.py` / `compare.py` / `build_room.py` |
| Object storage (versioned plans and inputs) | *Proposed* | Keep each month's plan and assumptions as versions and show "change since last month" |
| Compute job runner | *Proposed* | Run long parallel solves outside the session and notify when done |
| MCP tools (query the plan, write approvals) | *Proposed* | Let the decision room's AI panel and other agents query the plan |
| Scheduled runs, notifications (Slack, calendar), meeting-note events | *Proposed* | Re-plan on a monthly schedule and on Secretary.io meeting notes; notify decision deadlines |

<Aside type="note" title="TypeScript example">
  A full example stitching these snippets together is being prepared at `examples/engine-mro-agent/` (`src/ingest.ts` ingestion, `src/run-monthly.ts` monthly run, `src/ui.ts` UI embedding). All code on this page uses only APIs that exist in the current SDK (`@work-with-ai/sdk`).
</Aside>

Common setup:

```typescript
import { KnowledgeClient, WorkAGI } from "@work-with-ai/sdk";

const endpoint = "https://api.workwithagi.dev";
const apiKey = import.meta.env.VITE_AGI_KEY;

const kb = new KnowledgeClient(endpoint, apiKey);
const api = WorkAGI.api(endpoint, apiKey);
const EXAMPLE = "cd examples/engine-shop-selection-mc && pip install -r requirements.txt";
```

## (1) Annual baseline plan (the implicit agreement)

| | |
|---|---|
| **Business question** | In a normal year, how many shop visits, how much spend, how many spares? Everyone agrees on rough numbers when budgeting — we want them with a basis |
| **Who uses it** | Maintenance planning and finance (annual budget), executives (mid-term plan) |

**Flow with the SDK** — put reliability data and shop history into knowledge and have an agent run the 20-year life-cycle simulation to produce the norms and the current fleet state.

```typescript
await kb.upload(reliabilityCsv, "reliability-mtbur");     // unscheduled removal rate, EGT deterioration
await kb.upload(shopHistoryCsv, "shop-visit-history");    // past visits, cost, TAT

const baseline = await api.createSession({
  user_id: "planner-01",
  tool: "claude",
  label: "annual-baseline",
  prompt: [
    EXAMPLE,
    "Run python lifecycle.py --fleet-out data/fleet_visits_lifecycle.json and tabulate",
    "yearly shop visits by workscope, maintenance spend and spares on the shelf.",
    (await kb.context("unscheduled removal rate, EGT margin deterioration, cost and TAT by workscope", 8)).context,
  ].join("\n"),
});
```

**What you get**

- Yearly visits, spend and spare levels in steady state. These are fixed as the **baseline plan**; every other use case is shown as a delta from it.
- The input for the two-year window (`fleet_visits_lifecycle.json`), starting from the state that past operation actually produces rather than from a blank slate (44 visits due in two years in the synthetic example).

<Aside type="note">
  Freezing the baseline as a version and computing deltas automatically is part of the object-storage proposal. The example currently goes as far as using the `lifecycle.py` steady-state values as the budget baseline.
</Aside>

**Analysis scripts**: `lifecycle.py`

## (2) Monthly induction decisions (do we need to hurry?)

| | |
|---|---|
| **Business question** | Which engines must be decided this month? Which plan do we adopt, and who approves what? |
| **Who uses it** | Maintenance planners (monthly planning meeting), department heads (approval) |

**Flow with the SDK** — the planner pane runs the computation and writes the report, the reviewer checks assumptions, and the work is embedded in the planner's screen.

```typescript
const month = await api.createSession({
  user_id: "planner-01",
  tool: "claude",
  label: "monthly-2026-10",
  prompt: [
    EXAMPLE,
    "Run python compare.py --workers 4 --fragment to compare the seven methods.",
    "Then run python decide.py and python build_room.py to create report.html and room.html.",
    "Summarise in 10 lines: engines to decide this month, their deadlines and reasons, approvals needed.",
  ].join("\n"),
});

await api.addPane(month.session_id, { tool: "claude", role: "reviewer" }); // checks assumptions and exceptions

WorkAGI.terminal({ container: "#planner-terminal", endpoint, apiKey, sessionId: month.session_id });
```

**What you get** (delta from baseline, synthetic data)

- **Engines to decide this month**: 1 under the stochastic plan (SAA). The rest can wait until their deadlines, so teardown results and updated quotes can be awaited.
- **Cancellation risk**: 77.9% for a plan that takes quotes at face value, 36.5% for a plan built on averages, 13.1% for the stochastic plan and 6.9% with risk aversion (CVaR λ=1). The mean cost is about 7,300 k$ lower than the face-value plan (146,477 → 139,174 k$).
- Any early-removal exceptions are listed with their reasons (watch-list engine, avoiding the peak season, …) in the report and the decision room.

**Analysis scripts**: `compare.py` (seven methods in parallel, chooser page), `decide.py` (report), `build_room.py` (decision room)

## (3) Shop and contract selection

| | |
|---|---|
| **Business question** | How many visits go to which of three shops? Are fixed-price contracts, extra slot reservations or an engine-pool membership worth paying for? |
| **Who uses it** | Procurement and contracts, maintenance planners |

**Flow with the SDK** — ingest the quotes; the agent turns each into a "price + risk distribution" JSON. Because this involves contract interpretation, a reviewer pane checks the basis.

```typescript
await kb.upload(inHouseQuotePdf, "quote-in-house");
await kb.upload(oemQuotePdf, "quote-oem-net");
await kb.upload(indMroQuotePdf, "quote-ind-mro");
await kb.upload(overrunHistoryCsv, "findings-overrun-history");

const terms = await kb.context(
  "quoted price, currency, TAT, overrun cost sharing, slot booking lead time, expedite fee, minimum volume per shop", 10);

const shops = await api.createSession({
  user_id: "procurement-01",
  tool: "claude",
  label: "shop-selection",
  prompt: [
    EXAMPLE,
    "From the excerpts, write my_quotes.json in the format of data/shop_quotes.json; record the basis in notes.md.",
    "Run python run.py --shops my_quotes.json --json-out plan.json and python actions.py, then",
    "summarise visits per shop and the effect of contract actions (fixed price, extra slots, pool).",
    "--- excerpts ---", terms.context,
  ].join("\n"),
});
await api.addPane(shops.session_id, { tool: "claude", role: "reviewer" });
```

**What you get** (synthetic data)

- Visits per shop, compared on **expected cost, P90 and cancellation risk** rather than quoted price. The plan that accounts for uncertainty is about 1,400 k$ cheaper on average than the plan built on averages (140,596 → 139,174 k$).
- The delta of each contract action: leasing more spare engines was never chosen by the optimiser under any condition, because **an engine pool or flying the capacity with another type lowers cancellation risk more cheaply**.

<Aside type="caution">
  Reading overrun sharing and slot lead times from quotes involves contract interpretation. Always have procurement or contract staff check the agent's output (`notes.md`).
</Aside>

**Analysis scripts**: `run.py` (re-plan with replaced quotes), `actions.py` (contract actions), `levers.py` (single effect of common levers)

## (4) Asset strategy (spares, mid-life engines, part-out, fleet renewal)

| | |
|---|---|
| **Business question** | Should we buy mid-life engines instead of shop visits? Add spares? As new aircraft arrive, part engines out instead of overhauling them? |
| **Who uses it** | Executives, asset management, fleet planning |

**Flow with the SDK** — sweep the conditions nobody can pin down (used-engine prices, how many aircraft other fleets can lend) and solve each in its own agent session **in parallel**.

```typescript
const whatIfs = {
  explore: "python explore.py --workers 8",          // 5 factors × 108 combinations, classified by decision tree
  breakeven: "python sensitivity.py",                // mid-life price break-even; spare depth × substitution
  transition: "python actions.py",                   // actions incl. the 737-8 delivery case
};

const sessions = await Promise.all(
  Object.entries(whatIfs).map(([label, cmd]) =>
    api.createSession({
      user_id: "asset-01",
      tool: "claude",
      label: `asset-${label}`,
      prompt: `${EXAMPLE}\n${cmd}\nSummarise in 5 lines the conditions (thresholds) where the answer changes.`,
    })),
);
```

**What you get** (synthetic data)

- **The net price of a mid-life engine splits the decision most**: at 5,500 k$ or less, swapping in used engines for a third or more of the visits pays; at 6,500 k$ or more, shop visits only. Getting market quotes becomes the top action.
- With thin spares (the 156-engine condition), cancellation risk reaches up to 51% without substitution by other types, and falls to 6% with it.
- When new-aircraft deliveries build up, parting engines out instead of overhauling them enters the set of candidate actions.

**Analysis scripts**: `explore.py`, `sensitivity.py`, `actions.py`

## (5) Risk response (MRO congestion, LLP shortage)

| | |
|---|---|
| **Business question** | If external shop TAT grows, or LLP kits take 12 months, where does the plan break, and which requirement should we give up? |
| **Who uses it** | Head of maintenance planning, executives (risk meeting), procurement |

**Flow with the SDK** — when "the shops are congested" comes up in a meeting, re-solve the stress cases from that meeting note. Meeting-note events are proposed, so today the agent gets the notes via knowledge search.

```typescript
// Pick relevant remarks from knowledge that syncs Secretary.io meeting notes
const notes = await kb.search("engine shop TAT delay LLP delivery", 5);

const stress = await api.createSession({
  user_id: "planner-01",
  tool: "claude",
  label: "risk-backlog",
  prompt: [
    EXAMPLE,
    "Run python decide.py and summarise, for the base, MRO backlog, LLP crunch and combined stress cases,",
    "which requirements can no longer be met and which to give up so the rest hold.",
    "--- meeting notes ---",
    ...notes.results.map((r) => r.chunk),
  ].join("\n"),
});
```

**What you get** (synthetic data)

- For four cases (base / MRO backlog: external TAT +1 month / LLP crunch: half the kits on hand, 12-month lead time / combined stress), the change in cost and cancellation risk from the baseline.
- In an **LLP crunch**, giving up the lower-priority requirements (no extra spares, kits from stock only) keeps the cancellation-risk target, spare buffer and budget.
- Taking every cost at its pessimistic P90, no plan meets fiscal budgets, LLP kits and shop slots together — reported as a signal that the budget is only sufficient "on average".

**Analysis scripts**: `decide.py` (assumption cases and requirement priority), `actions.py` (actions in the MRO backlog case), `explore.py`

## Appendix: what is computed

Each script is explained in the README of the SDK repository examples.

- [`examples/engine-shop-selection-mc/`](https://github.com/working-with-agi/sdk/tree/claude/aircraft-engine-repair-optimization-8oww5m/examples/engine-shop-selection-mc) — two-stage stochastic programme treating quotes as price + risk distribution; report, decision room and analysis scripts (Python + PuLP + HiGHS + NumPy)
- [`examples/engine-mro-optimization/`](https://github.com/working-with-agi/sdk/tree/claude/aircraft-engine-repair-optimization-8oww5m/examples/engine-mro-optimization) — integrated model of removal timing × workscope × spares ([part 1](/en/showcase/engine-mro-optimization/))
- `examples/engine-mro-agent/` — the TypeScript snippets on this page as one example (in preparation)

In short, the computation has three steps.

```
1. Monte Carlo   generate N scenarios of quote overruns, TAT delays, FX and unscheduled removals
                 (findings are a property of the engine, so every shop gets the same random draws)
2. Stochastic    stage 1: shop, workscope, induction month and expedite per engine; long-term spares
   programme     stage 2: per scenario × month, fill shortfalls by short-term lease → other type → cancellation
   (SAA)         objective:   min E[total cost] + λ · CVaR90[total cost]   (λ = 0: risk neutral)
                 constraints: fiscal budget, LLP kits, shop slots, minimum volume, spare buffer, risk target
3. Evaluation    mean, P90, CVaR90 and cancellation risk on 5,000 independent scenarios; compare 7 methods
```

The decision deadline is:

```
deadline = planned induction month − longest lead time (shop slot booking, LLP kits not covered by stock)
```
